# design-sync notes — @verifiedinc-public/shared-ui-elements

## Fixes applied

- `[GENERAL]` `.storybook/preview.tsx` decorators (`withThemeFromJSXProvider` + `SnackbarProvider`) failed to bundle — esbuild has no default loader for `.woff2`, which the `@fontsource/lato/*.css` side-effect imports pull in. Fixed with an explicit `cfg.provider` chain (`ThemeProvider` -> `SnackbarProvider`) instead of trying to make the decorator bundle succeed. `ThemeProvider` isn't a package export, so it's added via `cfg.extraEntries` -> `.design-sync/extra/provider-entry.mjs`, which also precomputes the `theme({...})` call as `previewTheme` (referenced via `{"$ref": "previewTheme"}` — the decorator calls `theme()` with a `primaryFontFace` arg, which can't be expressed as a raw provider prop literal).
- `[GENERAL]` No static CSS (`[CSS_PLACEHOLDER]`/`[CSS_RUNTIME]`) — expected: this DS is MUI + emotion (CSS-in-JS), so there is no compiled stylesheet to scrape. Not chasing `cfg.cssEntry`.
- `[GENERAL]` `[FONT_MISSING]` risk: fonts (`@fontsource/lato` weights 300/400/700/900, `@fontsource/material-icons`) are only pulled in via side-effect CSS imports in `.storybook/preview.tsx`, invisible to the converter by default. Added them explicitly via `cfg.extraFonts` (the same 4 Lato weight CSS files + material-icons index.css) so real `@font-face` rules ship instead of a silent fallback-font match.
- `cfg.titleMap`: ~24 `Hooks/*` and `Utils/*`/`Styles/*` story titles excluded (`null`) — non-visual (hooks, color/phone utility demos, contrast checker), not part of the visual component surface a design agent would compose with.
- `cfg.titleMap`: `TextField`, `Counter`, `AnimateHeight` (actual export name `AnimatedHeight`) excluded (`null`) — these components exist in `src/` and compile into `dist/`, but are **not re-exported** from `src/components/index.ts` (TextField) or not barreled into the public component surface at all (`src/components/animation` isn't `export *`'d from `src/components/index.ts`). Since they aren't reachable via the package's public entry (`dist/index.mjs`), they aren't part of the shipped design system surface. Worth a ping to the DS maintainers — may be an oversight rather than intentional.
- `cfg.titleMap`: `"OneClickVerificationOutcomeOverTimeChart": "ConversionOverTimeChart"` — the story's `meta.title` names a chart variant, not the component; the story's own `component:` field confirms it renders `ConversionOverTimeChart`.
- `[GENERAL]` **DataTable's preview build never finished — memory climbed into tens of GB.** Root cause: `lib/story-imports.mjs`'s `ds-import-policy` esbuild plugin does `await b.resolve(...)` (a second async round-trip through the esbuild service) for _every single import in the whole graph_, including ones deep inside node_modules that could never be redirected. DataTable's story named-imports ~20 icons from `@mui/icons-material`, whose `esm/index.js` barrel re-exports ~2100 leaves — every one of those got the same double-resolve treatment (a plain `esbuild.build()` of the same file finishes in ~2.5s). Fixed with a fork: `.design-sync/overrides/story-imports.mjs` (declared via `cfg.libOverrides`) adds one early bail — `if (a.importer already under node_modules) return null` — before the expensive `b.resolve()`. If this repo's story-imports.mjs is ever re-forked for another reason, keep this bail; without it, any component importing enough of a large third-party barrel (icon packs, lodash-ish re-export files) can reproduce the same runaway.
- `[GENERAL]` **Headless chromium crashed ("Target crashed"/"Page crashed") partway through `package-validate.mjs`'s render-check**, ~20 previews into a single long-lived `page` shared across all 57 — every later `page.goto()` on the dead page then failed identically. `--disable-gpu` alone did NOT fix it. Patched `package-validate.mjs` directly (not forkable — it's a top-level staged script, re-copied fresh by `/design-sync` step 7.1's `cp -r`, so **this patch does not survive a re-sync** and may need reapplying by hand if the crash returns) with two things: (1) recycle the page every 5 renders instead of reusing one for all 57, and (2) on a "crashed" error, recreate the page and retry the same item up to 2 more times before giving up. This alone fixed ~53/57; the remaining 3 need per-component skips below. If the crash returns on a fresh clone, re-apply both to `.ds-sync/package-validate.mjs` (and the identical `pw.chromium.launch()` call in `.ds-sync/storybook/compare.mjs` / `probe.mjs`, patched the same way defensively).
- `cfg.overrides.SimpleBarChart.skip` (all 3 stories) — mounting `SimpleBarChart` (Recharts `ResponsiveContainer`) reliably crashes headless chromium ("Target crashed") on `page.evaluate` shortly after `page.goto` resolves — reproduced in total isolation (fresh browser, single story via `?story=Default`, no DOM walking at all — a bare `document.querySelectorAll('*').length` was enough to trigger it) and independent of `--disable-gpu`/reduced-motion. Not obviously data-dependent (`Default` is the simplest of its 3 stories: 2 static data points). Root cause not fully isolated — worth another look if this DS's Recharts version changes.
- `cfg.overrides.CredentialRequestsEditor.skip` (both stories) — its story uses a Storybook **loader** (`loaders: [loadCredentialRequests]`, consumed via `meta.render(args, { loaded: { credentialRequests } })`). Our compiled-preview wrapper's `ctx` has no `loaded` key (loaders are a Storybook-runtime feature this harness doesn't replicate), so `render` throws destructuring `undefined` and the mount is empty (`root empty`). Classic `sb-error`-class case (data-fetching before render) — skip is correct, not a converter bug.
- `cfg.overrides.CalendlyDialog.skip` (all 3 stories) — embeds a live `calendly.com` iframe widget. `page.goto(..., {waitUntil:'networkidle'})` timed out at 15s; egress to calendly.com itself is reachable from this shell (`curl` succeeds fast), so it's the widget's own continuous polling/beaconing defeating `networkidle`, not blocked egress.
- `cfg.overrides.SeriesPercentageChart.skip` (`Empty` story only) — throws `TypeError: Cannot convert undefined or null to object` in **both** our preview and the real reference storybook (`sb-error` verdict) — a genuine upstream bug in the story/component, not a harness issue. `Default` renders and grades fine.
- `cfg.overrides.<Name>.cardMode: "column"` batch-applied to the 25 components validate flagged `[GRID_OVERFLOW] ... wide` (AddressInput, AreaChart, BrandFilterInput, ConversionOverTimeChart, DateInput, DateRangeInput, ErrorCodesChart, ExportToPdfButton, NewOneClickForm, OneClickVerificationEventsOverTimeChart, OneClickVerificationFunnelChart, OneClickVerificationSuccessOverTimeChart, OverviewBigNumbers, PageHeader, PageSectionHeader, PieChart, RadioOption, ReasonCodesChart, RiskScoreBarChart, RiskScorePieChart, SeriesChart, SeriesChartLegend, SeriesPercentageChart, SynchronizedMetricsChart, TTSOverTimeChart, Typography) — all "wide" (cropped, not escaping), so `column` was the correct remedy per the decision tree; none needed `single`.
- `cfg.provider`: inserted `CssBaseline` between `ThemeProvider` and `SnackbarProvider` (re-exported via `.design-sync/extra/provider-entry.mjs`, same as `ThemeProvider`) — the real `.storybook/preview.tsx` decorator passes `GlobalStyles: CssBaseline` to `withThemeFromJSXProvider`, which our `cfg.provider` chain didn't reproduce. Turned out NOT to be the cause of an apparent Button/Paragraph/VerifiedImage size mismatch (see the grading note below — that was a false alarm), but it's a real fidelity gap regardless (matches what storybook actually wraps every story in) and costs nothing to keep.

## Grading — read before grading any more components

- **A "module"-kind component's DS-side compare screenshot is a FULL 900×700 VIEWPORT capture, not an element crop** (`storyShot()` in `compare.mjs` always does `dsPage.screenshot({fullPage:false})` — no element targeting). The storybook-side (`captureStory()`) IS a tight `el.screenshot()` crop. On the auto-shrunk sheet, this makes a perfectly correctly-sized DS component look dramatically smaller than its storybook reference purely from the framing difference — confirmed on Button, Paragraph, and VerifiedImage: all three looked like clear size mismatches on the sheet, but were byte-for-byte proportionally identical once viewed via the raw/ crops at native resolution (Button's DS-side computed style even matched stock MUI Button defaults: 14px font, `6px 16px` padding, 97×36.5px). **Always check `_screenshots/compare/raw/<...>__ds.png` next to `__sb.png` before grading a "module"-kind component as mismatch/close on size** — don't trust the sheet's apparent scale for this shape/kind. This is NOT an issue for "fallback"/grid-cell-cropped previews (`cellShot()` does element-crop both sides).

## Grading — animation timing (batches 1-3, wave 1)

- `[GENERAL]` **Framer-motion `animate()`/`AnimatePresence` content (count-up numbers, fade-in legends) isn't settled by `compare.mjs`'s stabilization** (`emulateMedia({reducedMotion:'reduce'})` + `page.clock.setFixedTime(...)` + screenshot `animations:'disabled'`) — that only catches CSS/WAAPI animations and frozen `Date`, not framer-motion's `requestAnimationFrame`-driven imperative style mutation. Confirmed independently in two waves:
  - `BigNumber` (`useCounter` hook -> framer-motion `animate()`, a real 1s count-up): both the storybook reference AND our preview land on a different, non-reproducible mid-count frame every capture. Hits `BigNumber`'s own `Default`/`With Formatter` stories and `OverviewBigNumbers`' 4 non-empty/non-loading stories. Graded `close` — no preview-level fix exists (both sides are non-deterministic, not just ours).
  - `SeriesChartLegend` (each row a framer-motion `<MotionStack>` in `<AnimatePresence>`, `initial={{opacity:0}}` -> `animate={{opacity:1}}`): same root cause, worse manifestation — an unsettled frame can land at opacity 0, making the WHOLE legend block invisible rather than just showing a wrong number. Hit `OneClickVerificationSuccessOverTimeChart` (3 stories), `SeriesChart` (3 stories), `TTSOverTimeChart` (4 stories), `SeriesChartLegend` itself (`Horizontal` fully blank, `Default` count drifts). Graded `mismatch`/`close` per story with notes.
  - Most severe: `SeriesPercentageChart`'s `Default` story — Recharts' own `isAnimationActive` mount-draw for the Area/Line is ALSO timer-gated, so the chart BODY (not just a legend) can render as a stuck pre-animation shape. Graded `mismatch`.
  - A batch-3 subagent's isolated repro pointed at `compare.mjs`'s clock-freeze specifically (chart stuck with stabilization on, fine within ~1s with it off); my own quick follow-up A/B test did not cleanly reproduce a stuck state (all 4 stabilization combinations rendered a complete curve) — likely confounded by that story's own `Math.random()`-seeded data varying per navigation (see the `AreaChart` note above for the same pattern). **Root mechanism not fully pinned down** — if this resurfaces, treat `compare.mjs`'s clock-freeze timing (frozen before vs. after the DS module's mount) as the prime suspect, not yet confirmed.
  - Not preview-fixable: the generated preview already compiles the story module verbatim; there's no story-level lever, and the animated component lives in the shared library, not story args. Accepted as `close`/`mismatch`-with-detailed-note per the grading rubric rather than worked around.
- `AreaChart` `ThreeSeries`/`CustomStyling` stories build data via `Math.random()` at module scope (`src/stories/components/chart/AreaChart.stories.tsx`), so even the real storybook reference re-randomizes every load — graded `close`; an owned `.design-sync/previews/AreaChart.tsx` pins fixed data so at least our side is internally deterministic (can't force a pixel match against a non-deterministic reference either way). `Default` uses static data and matches.
- `RiskScorePieChart`'s "With Legend Label" story: the bottom pie-slice annotation visually overlaps the first legend row identically on both storybook and preview (legend `mt: 2` isn't enough clearance once labels wrap to 3 lines) — a real, pre-existing component layout quirk, not a sync defect. Graded `match` (both sides show the same overlap). No action needed.
- `[PORTAL?]` was flagged by validate/compare on `AreaChart`, `ConversionOverTimeChart`, `ErrorCodesChart`, `OneClickVerificationEventsOverTimeChart`, `OneClickVerificationSuccessOverTimeChart` (all Recharts-based, `portal: true` in their `.cache/compare/*.json`) — grading subagents checked exhaustively and found no actual overlay bleed in any per-story raw crop (captures are isolated per `?story=`, so cross-cell bleed wouldn't show there anyway). These already have `cardMode: "column"` (for the separate `[GRID_OVERFLOW] wide` reason); left as-is rather than also switching to `"single"` — revisit only if the PRODUCT grid card (not the compare capture) is ever visually spot-checked and shows real bleed.

## Grading — wave 2 findings

- `PoweredByVerified` `White`/`White Green` stories rely on Storybook's `backgrounds` addon (`parameters.backgrounds.default = 'dark'`) to paint a dark canvas — the compiled-preview harness has no concept of that addon, so those two variants (white text) rendered invisible against a white page. Fixed with an owned `.design-sync/previews/PoweredByVerified.tsx` wrapping just those two variants in an explicit `Box sx={{bgcolor:'#333333'}}` matching Storybook's default dark swatch. Only this component's story references `backgrounds` in this repo (grepped), so not worth a converter-level fix — but if another story ever sets `parameters.backgrounds`, expect the same invisible-render failure.
- **On a "module"-kind component whose sheet cells look pattern-different (not just scale-different)** — e.g. `QRCodeDisplay`'s QR code looked like a different encoded value at thumbnail zoom — **verify pixel/data content directly before grading mismatch** (bit-grid extraction confirmed 0-cell disagreement; it was the same full-viewport-vs-crop framing artifact, just more visually confusing on dense/textured content than on text or shapes). Don't trust an eyeball read on this kind of content at sheet zoom.
- `[GENERAL]` **`compare.mjs`'s DS-side capture is viewport-capped, not just differently-framed.** `dsPage.screenshot({fullPage:false})` on a fixed 900×700 viewport means any component taller than ~700px gets REAL content cut off (not just an apparent-scale illusion) — confirmed on `NewOneClickForm`'s `Default` story: storybook's raw PNG is 712×1400 (full form), ours is 900×700 (Health Insurance section + Submit button never captured). Not preview-fixable — the component renders fully at runtime, only the verification screenshot is short. **Fixed** with `cfg.overrides.NewOneClickForm.viewport: "900x1500"` (full rebuild, since viewport moves the capture contract) — the full form now captures correctly, including the Submit button (which turned out to have its own, unrelated theme-color bug — see the `[GENERAL]` theme/styled-engine entry above). If another tall multi-section component (a long form, a table with many rows) ever grades suspiciously well despite looking incomplete, check its raw DS crop's actual pixel dimensions with `sips -g pixelHeight` before trusting a `match`.
- `[GENERAL]` **Three components render MUI's stock unthemed primary blue (`#1976d2`) instead of the DS theme's green (`palette.primary.main = colors.green` per `src/styles/theme.ts`): `TTSMagicButton` (its own themed CTA button), `TTSMagicQRCode` (the Download PNG/SVG buttons), and `NewOneClickForm` (the story-authored Submit button in `CredentialForm.stories.tsx`).** Root-caused via a React-fiber probe against the built HTML: the `ThemeProvider` chain correctly receives `theme.palette.primary.main === '#0dbc3d'` as a prop at every level, but the affected `Button`'s actually-emitted Emotion CSS rule hardcodes MUI's factory default — i.e. the styled-engine instance consuming the theme isn't the one `ThemeProvider` populated (a duplicate Emotion-cache/styled-engine instance, not a theme-value bug: `cfg.provider`/`previewTheme` is confirmed correct, since the DS's own `Button` component wrapper — compiled the same way — renders the correct green/blue for its Primary/Secondary stories).
  - **"Story imports raw `@mui/material` `Button`" is NOT the trigger** — ruled out directly: 15 story files import `Button` from `@mui/material` alongside DS components (grep across `src/stories/`), including `Alert.stories.tsx` (renders a bare, unstyled-override `<Button>Action</Button>` in its own demo harness) which grades `match` with the correct theme green. Only 3 of those 15 are actually broken, and the broken 3 don't share an obvious differentiator (one is the real shipped component's own internal Button — `magic-button.tsx`'s `color='primary'`; the other two are story-authored demo/submit buttons). **Root mechanism not confirmed** — a duplicate Emotion-cache/styled-engine instance (from `_preview/<Name>.js` separately bundling `@mui/material` since third-party imports are "never redirected" per `lib/story-imports.mjs` Rule 2) remains the leading hypothesis but is unproven; something about component/story complexity, render timing, or effect ordering may gate whether the duplicate actually wins the page's style-insertion point.
  - **No fix applied.** `cfg.storyImports.shim`ing `@mui/material` isn't safe — our bundle's own `Button` export is a DIFFERENT (custom) component, so shimming `@mui/material`'s `Button` to `window.<GLOBAL>.Button` would silently substitute the wrong component everywhere. A real fix needs either an `@mui/material`-aware redirect (shim third-party UI-library imports to the bundle's _own_ already-loaded copy of that same library, keyed by package not by DS-export-name collision) or accepting this as a narrow, structural gap. Affects 3 of 57 components; if a 4th ever turns up, that's a stronger signal worth another investigation pass.
  - (One false lead checked and ruled out along the way: a wave-2 subagent flagged `Button`'s own "Secondary" story as possibly showing this same swap — re-verified directly via raw crops, it's correctly blue on both sides; no bug there.)
- `cfg.overrides.OTPInput.skip` (`OTP Within Iframe` story only) — mounts the component inside a real `<iframe srcDoc>` via `createPortal`, with a story-local Emotion `CacheProvider` scoped to the iframe's own `document.head` (`src/components/__for-stories/Iframe.tsx`) — the compiled bundle's MUI/emotion styles never reach that iframe's head, so it renders unstyled with zero salvageable content. Not preview-fixable (verbatim story compile, no lever); skipped rather than left as a permanent `mismatch` since there's nothing correct to show. `Default`/`With Error`/`OTP With Controls` all match cleanly.
- `cfg.overrides.SeriesChartLegend.skip` (`Horizontal` story only) — entrance-animation timing (see the animation-timing entry above) leaves this story's legend fully blank (opacity:0, never ticks) with no correct content underneath to salvage; skipped rather than left as a permanent `mismatch`. `Default` is a `close` accept (drifted Counter values, same root cause, but at least renders).
- `[GENERAL]` **`infinite` CSS keyframe animations aren't settled by `compare.mjs`'s stabilization either** (extends the framer-motion/Recharts finding above to plain CSS) — `PrettyPhoneInput`'s `::before` conic-gradient border effect (three simultaneous `infinite` animations: rotate 8s, pulse 3s, move 12s) shows a visible highlight-streak artifact in our capture that storybook's reference doesn't show. Playwright's screenshot `animations:'disabled'` only finishes finite CSS animations/transitions/WAAPI, not infinite ones (there's no "end state" to jump to) — the two independently-navigated pages just land on different points in the infinite loop. Hits `PrettyPhoneInput` (all 6 stories) and `PhoneInput`'s "Pretty" story (same underlying component). Graded `close` — no fix exists; the animation is intrinsic to the shared component's CSS, not story-authored.

## Re-sync risks

- If the DS maintainers later add `TextField`/`Counter`/`AnimatedHeight` to the public barrel, the `titleMap: null` exclusions above should be revisited (they'd then be real, addressable components).
- `cfg.provider`'s `previewTheme` is a snapshot of `theme({ primaryFontFace: { style: { fontFamily: 'Lato' } } })` — if the theme's construction args change meaningfully in `.storybook/preview.tsx`, update `.design-sync/extra/provider-entry.mjs` to match.
- `SnackbarProvider`'s `Components={{ customAlertComponent: CustomAlertComponent }}` prop from the real decorator is NOT reproduced (provider props are single-level literals/`$ref`s only) — any component whose preview specifically exercises the `customAlertComponent` snackbar variant may render the default notistack alert instead.
- **The `package-validate.mjs` page-recycling/crash-retry patch above is NOT persisted** — it's a hand-edit to a top-level staged script that `/design-sync` step 7.1 re-copies fresh from the skill's bundled copy on every run (there's no fork mechanism for top-level scripts, only for `lib/*.mjs`). If a future sync's render-check starts crashing again around ~20 previews in, this is why — reapply the same two changes (page recycling every 5 items; retry-with-fresh-page on a "crashed" error, up to 2 retries) to `.ds-sync/package-validate.mjs`'s render-check loop.
- If Recharts is ever upgraded, re-test `SimpleBarChart` without its skip — the crash may have been a version-specific Recharts/headless-chromium interaction.
- If `CredentialRequestsEditor`'s story ever drops its `loaders:` pattern in favor of static `args`, remove its skip — it would then be capturable.
